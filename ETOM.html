Canonical Definition

The Event Temporal Order Module (ETOM) governs how a Tax-Relevant
Event is positioned within a relevant temporal sequence after its
Event Time, Event Start, Event Completion, and Event Duration
have been sufficiently governed.

ETOM establishes whether the governed event occurred before,
after, during, concurrently with, overlapping, or within another
relevant temporal condition or event, while preserving
uncertainty, partial ordering, distributed timing, and supported
temporal precision.

Its specific task is:

to establish the governed temporal position of the event relative
to relevant events and temporal references without converting
temporal sequence into causation, legal priority, tax-period
assignment, or jurisdiction-specific tax consequence.

ETOM transforms the completed temporal governance structure of
TRETS into a:

Governed Temporally Situated Event

This becomes the canonical TRETS output for downstream Event
Location governance. ------------------------------ 1.
Operational Role

ETIM identifies temporal information legitimately associated with
the event.

ETSM establishes its operational start.

ETCM establishes its operational completion.

ETDM establishes its governed duration.

ETOM establishes where that temporally governed event stands
relative to other relevant temporal objects.

The principal transition is:

Governed Event Time + Governed Event Start + Governed Event
Completion + Governed Event Duration

↓

Governed Event Temporal
Order

↓

Governed Temporally Situated Event

Temporal order answers questions such as: Did Event A occur
before Event B? Did Event B begin while Event A remained active?
Did two events occur concurrently? Did their temporal spans
overlap? Can only a partial ordering be established? Does
available evidence support sequence but not exact timestamps? Are
distributed components temporally synchronized? Does uncertainty
prevent definitive ordering?

ETOM governs these temporal relationships.

It does not determine why one event followed another.

Temporal Order ≠ Causal Relationship.

------------------------------ 3. Operational Space

ETOM governs the operational space in which the temporal position
of a Tax-Relevant Event must be established relative to relevant
temporal references.

This includes: event-before-event ordering, event-after-event
ordering, simultaneous events, concurrent events, overlapping
events, nested temporal structures, partially ordered events,
distributed event ordering, machine event ordering, autonomous
event ordering, sequence uncertainty, sequence conflict, temporal
equivalence, temporal precedence, temporal succession, temporal
traceability, temporal-order correction.

ETOM does not own semantic Event Relationships governed later by
TRERLS.

Its concern is specifically:

when events stand relative to one another.

Relationships, legal priority, tax jurisdiction, tax period,

Relevant Temporal Reference Identification

An event cannot be meaningfully ordered against every event in a
system.

ETOM must first identify the temporal references relevant to the
governed purpose.

Possible temporal references include: another Governed Event, a
governed operational milestone, a machine operation, an
autonomous action, a transaction event, a physical event, a
digital event, a system state transition, an external temporal
reference, a governed temporal boundary.

Relevance must be operationally justified.

Available Event ≠ Relevant Temporal Reference by Default.
------------------------------ 6. Temporal Comparison

Once relevant temporal references are identified, ETOM compares
their governed temporal structures.

The comparison may use: Governed Event Time, Governed Event
Start, Governed Event Completion, Governed Event Duration,
supported temporal precision, uncertainty states, temporal
intervals.

Temporal comparison must use governed temporal outputs rather
than arbitrarily selected raw timestamps.

Timestamp Comparison ≠ Governed Temporal Comparison by Default.
------------------------------ 7. Temporal Precedence

Temporal precedence exists where sufficient governed temporal
information establishes that one event occurred before another
relevant event or temporal condition.

Conceptually:

Event A

↓

Event B

may establish:

Event A Temporally Precedes Event B

This statement concerns sequence only.

It does not establish: causation, dependency, responsibility,
authorization, economic relationship, legal priority, tax
consequence.

Temporal Precedence ≠ Causation. ------------------------------
8. Temporal Succession

Temporal succession establishes that an event follows another
event or temporal reference.

For example:

Event A completes

↓

Event B begins

may support:

Event B Temporally Succeeds Event A

However, temporal succession alone does not establish that Event
A produced, triggered, authorized, or required Event B.

Temporal Succession ≠ Dependency.

Semantic relationships between events remain governed by:

TRERLS — Tax-Relevant Event Relationship Standard
------------------------------ 9. Simultaneous Events

Two events may have temporal representations indicating the same
temporal position.

However, apparent timestamp equality does not automatically
establish true simultaneity.

For example:

Event A: 10:14:23

Event B: 10:14:23

may reflect only one-second recording precision.

The events may actually have occurred hundreds of milliseconds
apart.

ETOM must therefore distinguish:

Same Recorded Timestamp

from:

Governed Temporal Simultaneity

Timestamp Equality ≠ Event Simultaneity by Default.
------------------------------ 10. Concurrent Events

Events are concurrent where their governed temporal execution
exists during at least part of the same relevant temporal
interval while remaining distinct governed events.

For example:

Event A: 10:00–10:20

Event B: 10:05–10:15

Event B occurs during the active temporal span of Event A.

This establishes concurrency.

It does not establish that the events are part of the same
economic activity or that one caused the other.

Temporal Concurrency ≠ Event Unity.
------------------------------ 11. Temporal Overlap

Two events overlap where their governed temporal spans intersect.

For example:

Event A: 08:00–11:00

Event B: 10:30–12:00

produces an overlap from:

10:30–11:00

ETOM may preserve: overlap existence, overlap start, overlap
completion, overlap duration, overlap precision, overlap
uncertainty.

Overlap is a temporal property.

Temporal Overlap ≠ Operational Dependency.
------------------------------ 12. Nested Temporal Structures

One governed event may occur entirely within the temporal span of
another event.

For example:

Event A: 08:00–18:00

Event B: 11:00–12:30

Temporal structure:

Event A Start

↓

Event B Start

↓

Event B Completion

↓

Event A Completion

ETOM may represent Event B as temporally nested within Event A.

This does not automatically make Event B a component, child,
sub-event, or dependent event of Event A.

Those are separate governance questions.

Temporal Containment ≠ Structural Containment.
------------------------------ 13. Partial Temporal Ordering

Complex systems frequently contain sufficient information to
establish some ordering relationships without supporting a
complete timeline.

For example:

A occurred before B

and:

C occurred after A

but available information cannot determine whether:

B occurred before C

or:

C occurred before B

ETOM must support:

Partial Temporal Order

rather than fabricate a complete sequence.

A legitimate partial ordering is preferable to false precision.

Incomplete Order ≠ Invalid Temporal Governance.
------------------------------ 14. Temporal Equivalence

Where available governed information cannot distinguish the
temporal ordering of two events at the supported precision, ETOM
may represent them as temporally equivalent within that
precision.

For example:

Event A: approximately 14:00

Event B: approximately 14:00

If no legitimate finer-grained evidence exists, ETOM must not
invent an order.

Insufficient Ordering Precision ≠ Permission to Infer Sequence.
------------------------------ 15. Distributed Event Ordering

Distributed systems may produce events across: multiple servers,
multiple machines, multiple geographic locations, multiple
networks, multiple time zones, asynchronous infrastructure.

Local clocks may not be perfectly synchronized.

Event A may appear earlier than Event B in raw timestamps while
system latency or clock drift indicates that the true order is
uncertain.

ETOM must distinguish:

Recorded Distributed Order

from:

Governed Distributed Temporal Order

Where deterministic ordering cannot be supported, ETOM should
preserve partial or uncertain ordering.

Distributed Timestamp Order ≠ Governed Event Order by Default.
------------------------------ 16. Machine Event Ordering

Machine environments can generate millions of temporal signals.

Sequence numbers, log timestamps, processing timestamps,
telemetry timestamps, database commits, message queues, and
execution clocks may represent different temporal semantics.

ETOM must not assume that the order in one technical log
represents the operational order of governed events.

It must use the governed timing structure established through
TRETS.

Log Order ≠ Event Order by Default.
------------------------------ 17. Autonomous Event Ordering

Autonomous systems may initiate and execute multiple events
without direct human sequencing.

For example:

Agent Decision A

Machine Action B

External Response C

Agent Replanning D

may occur across overlapping computational and physical
timelines.

ETOM governs their temporal positions without determining
whether: A caused B, C justified D, the agent possessed
authority, a participant bears responsibility.

Those questions belong to other governance spaces.

Autonomous Sequence ≠ Autonomous Authority.
------------------------------ 18. Event Order Across Time Zones

Events may be recorded in different local time zones.

For example:

09:00 Zurich

and:

16:00 Singapore

cannot be ordered merely by comparing displayed local clock
values.

ETOM must preserve: original local timestamp, time zone, offset,
normalized comparison time where legitimate, normalization
method, supported precision.

Normalization may support comparison.

It must not erase the original temporal representation.

Normalized Time ≠ Original Recorded Time.
------------------------------ 19. Clock Synchronization

Distributed environments may use clocks with different
synchronization states.

Potential issues include: clock drift, delayed synchronization,
incorrect device time, network latency, timestamp buffering,
offline operation, asynchronous transmission.

ETOM must preserve the effect of these conditions on temporal
ordering.

Clock Precision ≠ Clock Accuracy.

Clock Synchronization ≠ Event Synchronization.
------------------------------ 20. Timestamp Collision

A timestamp collision occurs when multiple events receive the
same timestamp despite being distinct and potentially sequential
events.

This may occur because of: limited timestamp precision, batch
processing, synchronized recording, system architecture, database
constraints.

ETOM must not arbitrarily order events solely because a database
returns them in a particular sequence.

Database Record Order ≠ Governed Temporal Order.
------------------------------ 21. Temporal Order Precision

Temporal ordering can only be established at the precision
supported by governed temporal information.

Possible precision levels may include: date, hour, minute,
second, millisecond, microsecond, bounded interval, approximate
temporal range.

If two events occur within the same supported temporal interval,
their exact internal ordering may remain unresolved.

Technical Precision ≠ Operational Temporal Precision.
------------------------------ 22. Temporal Order Uncertainty

Temporal-order uncertainty exists where the available governed
information does not support a definitive sequence.

ETOM may represent:

Order Established

Order Probable

Order Partial

Order Equivalent at Supported Precision

Order Conflicted

Order Unresolved

Uncertainty must remain explicit.

Temporal Uncertainty ≠ Permission for Arbitrary Ordering.
------------------------------ 23. Temporal Order Conflict

Conflict exists where credible temporal sources support
incompatible orderings.

For example:

System A indicates:

Event X

↓

Event Y

while System B indicates:

Event Y

↓

Event X

ETOM must evaluate the governed temporal structures and preserve
unresolved conflict where legitimate resolution is unavailable.

The system must not select whichever sequence produces a
preferred downstream outcome.

Preferred Outcome ≠ Valid Basis for Temporal Ordering.
------------------------------ 24. Temporal Order Correction

New evidence may justify correction of an established temporal
order.

Correction must preserve: prior order, revised order, affected
events, supporting temporal information, reason for correction,
correction authority, version continuity, traceability.

Where correction reveals that Event Start, Completion, Duration,
or Time Identification was incorrect, the issue must be routed to
the relevant TRETS module.

Temporal Order Correction ≠ Historical Erasure.
------------------------------ 25. Temporal Order and Causation

ETOM establishes sequence.

It does not establish causation.

The observation:

Event A occurred before Event B

does not establish:

Event A caused Event B.

Similarly:

Event B occurred while Event A was active

does not establish:

Event B is part of Event A.

Temporal evidence may later contribute to relationship,
investigation, attribution, or accountability analysis.

ETOM itself does not make those determinations.

Before ≠ Because Of. ------------------------------ 26. Temporal
Order and Event Relationships

TRERLS later governs Event Relationships, including relevant
dependencies, sequences, groupings, merges, and splits at the
architecture relationship layer.

ETOM supplies governed temporal structure that such analysis may
consume.

ETOM owns:

Temporal Sequence

TRERLS owns:

Governed Event Relationship

Therefore:

Temporal Sequence ≠ Event Relationship by Default.
------------------------------ 27. Temporal Order and Legal
Priority

Legal systems may assign significance to event order.

Examples may include: priority, recognition, filing sequence,
settlement precedence, contractual effects, statutory timing.

ETOM does not determine those legal consequences.

It establishes governed operational temporal order for downstream
interpretation.

Operational Temporal Priority ≠ Legal Priority.
------------------------------ 28. Temporal Order and Tax
Determination

Tax systems may interpret event sequence when determining: tax
point, tax period, recognition timing, reporting obligation,
jurisdictional treatment, transaction treatment.

ETOM does not perform those determinations.

Its output remains jurisdiction-neutral.

Temporal Order ≠ Legal Tax Point.

Temporal Order ≠ Tax Period Determination.

Temporal Order ≠ Taxability Determination.

------------------------------ 32. Governance Logic

The minimum ETOM governance logic is:

IF relevant events possess sufficiently
governed temporal structures,

THEN their temporal positions may be compared.

IF Event A completes before Event B
begins,

THEN temporal precedence may be established.

IF Event B follows Event A,

THEN succession may be established without inferring dependency.

IF governed temporal spans intersect,

THEN temporal overlap may be established.

IF distinct events remain active during
the same temporal interval,

THEN concurrency may be established.

IF one event occurs entirely inside
another event's temporal span,

THEN temporal containment may be represented without inferring
structural containment.

IF only some ordering relationships can be
supported,

THEN ETOM must preserve a partial order.

IF timestamps are equal only because of
limited precision,

THEN simultaneity must not be assumed.

IF distributed clocks conflict,

THEN raw timestamp order must not automatically determine
governed order.

IF sequence remains uncertain,

THEN uncertainty must remain explicit.

IF credible temporal evidence conflicts,

THEN conflict must not be resolved according to preferred
downstream outcome.

IF temporal order changes because upstream
temporal governance changes,

THEN ETOM must preserve correction history and reconstruct the
order.

IF temporal sequence is established,

THEN causation must remain a separate governance question.

IF a jurisdiction assigns legal
significance to sequence,

THEN that determination remains outside ETOM.

Case 1 — Global Marketplace with Concurrent Commercial Events

A global marketplace records a sequence involving: customer order
submission, payment authorization, seller acceptance, inventory
reservation, invoice generation, shipment release, payment
settlement.

The systems operate across different countries and time zones.

The order is recorded at:

10:00:02

Payment authorization begins at:

10:00:03

Inventory reservation begins at:

10:00:03

Seller acceptance is recorded at:

10:00:05

Payment authorization completes at:

10:00:06

Inventory reservation completes at:

10:00:07

Invoice generation occurs at:

10:00:08

A simple database listing may present these records sequentially.

ETOM establishes that payment authorization and inventory
reservation were partially concurrent rather than mechanically
treating one as preceding the other.

It also preserves that seller acceptance occurred during both
operational processes.

ETOM does not infer that payment authorization caused seller
acceptance or that invoice generation represents the legal tax
point.

It produces a governed temporal sequence that downstream
relationship and jurisdictional tax systems may interpret
independently.

The order in which systems record commercial activity must not
silently become the legal meaning of that activity.
------------------------------ 38. Real-System Use Case 2 —
Autonomous Industrial Network with Unsynchronized Machine Clocks

An autonomous industrial network contains three machines and an
AI orchestration agent.

Machine A records an operational event at:

14:22:10.480

Machine B records a response at:

14:22:10.320

The orchestration agent records its instruction at:

14:22:10.410

Raw timestamps appear to indicate:

↓

Agent Instruction

↓

However, governance data shows: Machine A clock is synchronized;
the orchestration agent clock is 40 milliseconds behind; Machine
B clock is approximately 240 milliseconds behind; network
transmission introduces variable latency.

The raw timestamp sequence therefore cannot legitimately
establish operational order.

ETOM normalizes and qualifies the available temporal information
while preserving the original timestamps and synchronization
uncertainty.

Where evidence supports only:

Machine A Event

↓

Agent Processing

↓

Machine B Response

within bounded temporal ranges, ETOM records that governed
sequence.

Where exact micro-ordering remains unsupported, it remains
unresolved.

ETOM does not infer responsibility, causation, authority, or
liability from the sequence.

The resulting structure can be consumed by downstream governance
architectures without corrupting operational reality through
misleading timestamp precision.

In distributed autonomous systems, the earliest timestamp is not
necessarily the earliest event. ------------------------------

Canonical Closing Statement

ETOM completes the temporal governance of the Tax-Relevant Event
by establishing where the event stands in operational time
relative to relevant events and temporal references while
preserving uncertainty, concurrency, distributed timing, and the
boundary between sequence and meaning.

Temporal order can establish what came before, after, during, or
alongside an event. It cannot, by itself, establish why it
happened, what caused it, or what legal consequence follows.

TRETS governs when the event occurred as governed operational
reality — not when tax law decides that the event becomes
taxable.

TREGA™ governs the event. The jurisdiction governs the tax.
