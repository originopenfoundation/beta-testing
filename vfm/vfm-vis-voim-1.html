Canonical Definition

Value Object Identification Module (VOIM) is the first Core Module of the Value Identification Standard (VIS) within VFM® — Value Flow Mechanisms Architecture.

VOIM governs the methodological identification of the precise Value Object whose value is to be governed through the value lifecycle.

The Module establishes whether a sufficiently identifiable object, capability, resource, activity, relationship, right, condition, information object, physical object, digital object, service, process, outcome, opportunity, or other governable subject exists to serve as the reference object to which value may relate.

VOIM separates three concepts that must not be treated as equivalent:

Underlying Object ≠ Value Object ≠ Value

An underlying object may exist without becoming relevant to a particular value lifecycle.

A Value Object is the explicitly identified subject in relation to which value is being examined.

Value itself is the governed phenomenon whose lifecycle VFM® subsequently governs.

VOIM does not determine whether the identified Value Object actually possesses value, how much value exists, where that value originated, or whether value has yet emerged.

Its foundational task is narrower:

to establish exactly what the value lifecycle is about before any determination concerning value origin, emergence, recognition, state, change, development, degradation, nullification, restoration, or extinction is made.

Core Question

What exactly is the Value Object whose value lifecycle is to be governed?

Architectural Position

VOIM is the first Core Module of the first Parent Standard of VFM®.

It therefore establishes the initial methodological entry point into the complete value lifecycle.

Before VFM® asks:

Where does value originate?

it must first know:

What is the object in relation to which value is being examined?

The sequence begins:

Potential Value-Relevant Subject → Value Object Candidate → Identification Basis → Value Object Determination → Governable Value Object

The identified Value Object can then proceed through the remaining modules of the Value Identification Standard before entering Value Origin Standard.

Internal Flow Position

Potential Value-Relevant Subject → Value Object Candidate Identification → Object Reference Definition → Object Type Determination → Object Distinguishability Assessment → Object Context Identification → Object Version / State Reference → Value Object Determination → Value Object Identifier → Governable Value Object → Value Object Boundary Module

Operational Space

VOIM governs the space between:

something that may be relevant to value

and

a sufficiently identified Value Object capable of entering governed value analysis.

This operational space includes:

Value Object Candidate identification; object reference; object distinguishability; object type; object form; object configuration; object version; object temporal reference; object contextual reference; composite-object identification; component-object identification; relationship-object identification; capability identification; activity identification; process identification; outcome identification; opportunity identification; Value Object determination; Value Object identifier; Value Object traceability.

Value Object Concept

For VFM®, a Value Object is:

a sufficiently identifiable and distinguishable subject in relation to which a specific value lifecycle may be governed.

A Value Object may be tangible or intangible.

It may be persistent or temporary.

It may already exist physically or digitally, or represent a sufficiently defined capability, relationship, opportunity, activity, process, or outcome.

Examples may include:

land; buildings; machinery; raw materials; infrastructure; energy capacity; software; algorithms; datasets; intellectual property; patents; licenses; contractual rights; services; skills; capabilities; processes; production capacity; organizations;

projects; relationships; access rights; information; knowledge; opportunities; environmental resources; digital assets; operational capabilities; future sufficiently defined value-bearing subjects.

The list is intentionally non-exhaustive.

VFM® must remain capable of governing value associated with forms of objects that do not yet exist today.

Underlying Object ≠ Value Object

An object does not automatically become a Value Object merely because it exists.

Consider a building.

The underlying object may be:

Building A

But different value inquiries may concern:

Building A as operational production capacity

Building A as rentable space

Building A as redevelopment potential

Building A as material recovery potential

Building A as strategic location

The physical object may be the same.

The Value Object reference may differ according to what exactly is entering the governed value lifecycle.

VOIM therefore prevents the existence of an underlying object from being mistaken for sufficient identification of the Value Object.

Value Object ≠ Value

This distinction is foundational to VFM®.

Value Object answers:

What is the subject whose value lifecycle is being examined?

Value answers a different question:

What value exists, originates, emerges, changes, develops, degrades, disappears, returns, or becomes extinct in relation to that subject?

A machine may be identifiable even where its economic use has disappeared.

A patent may remain identifiable even where its commercial value reaches zero.

A dataset may remain identifiable while its value changes across different contexts.

Therefore:

Object existence does not establish value existence.

And:

Value Object identification does not constitute Value Recognition.

Value Object Candidate

Before formal identification, a potential subject enters VOIM as a Value Object Candidate.

A Value Object Candidate is:

a subject proposed for entry into VFM® because a value lifecycle may exist in relation to it.

Candidate status does not establish:

value existence; value origin; value emergence; positive value; market value; financial value; legal value; ownership; validity; integrity; classification; price; monetary amount.

It establishes only that the subject requires examination as a possible Value Object.

Identification Basis

Every Value Object should have a sufficient Identification Basis.

Depending on the object, this may include:

name; reference number; physical description; digital identifier; location reference; technical configuration; version; temporal state; component structure; process definition; capability definition; relationship definition; contractual reference; project reference; dataset reference; asset reference; other sufficiently distinguishing characteristics.

The identification basis must be sufficient to answer:

Which exact object are we talking about?

Object Type

VOIM may classify the basic identification form of the Value Object for methodological navigation.

Examples may include:

Physical Object Digital Object Information Object Capability Resource Activity Process Service Right Relationship Opportunity Outcome Composite Object Other Governable Value Object

These are identification forms rather than universal economic classifications.

Formal classification governance remains within CLA™ — Classification Architecture where required.

Object Distinguishability Principle

A Value Object must be sufficiently distinguishable from other objects to permit its value lifecycle to be governed.

The object need not always be physically separable.

It must be methodologically distinguishable.

For example:

a production line

may be identifiable as one Value Object even though it contains hundreds of physical components.

Likewise:

production capacity

may constitute a Value Object even though the capability arises from a combination of machinery, people, processes, energy, knowledge, and infrastructure.

The requirement is not physical isolation.

The requirement is:

sufficient distinction for value governance.

Composite Value Objects

A Value Object may consist of multiple components.

Examples include:

an industrial facility; an infrastructure network; a business unit; a technology platform; a production system; a portfolio; an integrated capability.

VOIM must identify when the value inquiry concerns:

the composite object

rather than merely the sum of its individual components.

This distinction matters because:

Value of Composite Object ≠ Automatic Sum of Component Values

Interactions, dependencies, complementarities, constraints, network effects, configuration, and context may produce a different value lifecycle at the composite level.

Component Value Objects

A component of a larger object may itself become a separate Value Object where its value lifecycle requires independent governance.

Therefore:

Object A may contain:

Value Object A.1 Value Object A.2 Value Object A.3

while the complete system may simultaneously constitute:

Value Object A

Each lifecycle must remain distinguishable.

Multiple Values Associated with One Object

A single underlying object may support multiple distinct value lifecycles.

For example, a forest may carry:

timber value; carbon-related value; ecological value; recreational value; water-regulation value; strategic land value.

VOIM must therefore avoid assuming:

One Object = One Value

Instead:

One Object → Potentially Multiple Distinct Value Relationships

The subsequent modules and Parent Standards determine how those value relationships are bounded and governed.

Same Value Across Multiple Objects

Conversely, one value phenomenon may depend upon multiple underlying objects.

For example:

network value

may arise from the interaction of many participants.

production capability

may depend upon machinery, workforce, infrastructure, knowledge, and supply access.

VOIM must therefore support identification of:

Composite Value Objects

and

Relational Value Objects

where the relevant subject cannot legitimately be reduced to one isolated physical asset.

Value Object Context

Identification may require contextual information where the same object can function differently across environments.

Context may include:

intended use; operational environment; economic environment; temporal period; technological environment; organizational context; geographic context; dependency context; relationship context.

VOIM identifies relevant context necessary to distinguish the object.

It does not yet determine the value produced by that context.

Temporal Identification

A Value Object may change over time.

Therefore, identification should establish the relevant temporal reference where material.

For example:

Factory X — Configuration 2024

may not represent the same Value Object state as:

Factory X — Configuration 2026 after automation upgrade.

VOIM must preserve enough temporal distinction to prevent value analysis performed on materially different object states from being silently combined.

Version and Configuration Awareness

For digital, technological, industrial, organizational, or composite Value Objects, version and configuration may materially affect identification.

Relevant distinctions may include:

software version; model version;

machinery configuration; infrastructure configuration; organizational structure; production configuration; contractual configuration; dataset version; capability state.

VOIM does not govern configuration integrity.

It ensures only that the object being subjected to value governance is sufficiently identifiable.

Potential Value ≠ Existing Value

VOIM may identify a Value Object even where value has not yet emerged.

This is essential for the VFM® lifecycle.

A newly discovered technology may be identifiable.

A development site may be identifiable.

An unused patent may be identifiable.

An unexploited resource may be identifiable.

A future production capability may be identifiable.

None of this automatically means that value already exists.

Therefore:

Value Object Identification → does not imply → Value Emergence

This preserves the boundary with later VFM® Parent Standards.

Zero Value Does Not Eliminate the Value Object

A Value Object may remain identifiable after its relevant value reaches zero.

This is critical for the later VFM® concept:

ZVA™ — Zero Value Asset™

A zero-value condition does not necessarily mean that the underlying Value Object has ceased to exist.

The object may remain identifiable while:

Value State = Zero

and may later enter:

Value Restoration

where a legitimate restoration pathway exists.

Therefore:

Object Extinction ≠ Value Nullification

and

Zero Value ≠ Value Extinction

Value Object Identification State

VOIM may assign a governed identification state.

A minimum model may include:

1. Unidentified

A potentially value-relevant subject exists, but it has not been sufficiently identified.

2. Candidate

A subject has been proposed as a Value Object but requires additional identification.

3. Conditionally Identified

The subject is sufficiently identifiable only under specified contextual, temporal, configuration, or relational conditions.

4. Identified

The Value Object is sufficiently identified and distinguishable to proceed through VFM® governance.

5. Identification Suspended

A previously identified Value Object has materially changed or contains unresolved ambiguity requiring reassessment.

6. Identification Retired

The identification reference is no longer active for the governed value lifecycle but is preserved for traceability.

These states govern identification only.

They do not describe value state.

Identification State ≠ Value State

VOIM enforces:

Value Object Identification State ≠ Value State

An object may be:

Identified

while its value is:

unknown, emerging, positive, degraded, zero, restored, or extinct.

The two governance dimensions must remain separate.

VOIM Boundary with Value Object Boundary

Module

VOIM answers:

What is the Value Object?

The Value Object Boundary Module answers:

Where does that Value Object begin and end for the relevant value lifecycle?

Identification precedes boundary determination.

A subject cannot be meaningfully bounded before it is sufficiently identified.

VOIM Boundary with Value Differentiation &

Separation Module

VOIM identifies the subject.

The Value Differentiation & Separation Module determines whether multiple value phenomena, objects, components, or value relationships must remain analytically separate.

Therefore:

Identification ≠ Differentiation.

VOIM Boundary with Value Context & Condition

Module

VOIM may record context necessary to identify the object.

The Value Context & Condition Module governs the broader conditions under which the identified Value Object is being examined for value purposes.

Therefore:

Identification Context ≠ Value Context Governance.

VOIM Boundary with Value Origin Standard

VOIM identifies:

what the value lifecycle concerns.

The Value Origin Standard determines:

where the relevant value originates.

Therefore:

Value Object ≠ Value Origin

and:

Identification ≠ Origin Determination.

VOIM Boundary with Value Emergence Standard

VOIM does not determine whether value has actually come into existence.

That belongs to the Value Emergence Standard.

A Value Object may be fully identified while no value has yet emerged.

VOIM Boundary with Value Recognition Standard

VOIM does not recognize value.

It identifies the object to which a possible value lifecycle relates.

Therefore:

Object Identification ≠ Value Recognition.

VOIM Boundary with CLA™

VOIM may establish an identification type necessary to distinguish a Value Object.

It does not replace formal classification governance.

Where formal classification is required:

CLA™ — Classification Architecture governs classification.

VOIM Boundary with OBIDENITY®

VOIM does not determine:

legal identity; ownership; authority; permission; responsibility; provenance rights; transfer rights.

Where origin-bound identity governance is required, those questions remain within OBIDENITY® — Origin-Bound Identity Governance Architecture.

A Value Object may be identified for value governance without VFM® determining who owns it.

VOIM Boundary with VALIDOS®

VOIM does not determine whether the Value Object or any claim concerning it is valid.

VALIDOS® — Validation Governance Architecture governs validation.

Identification is a prerequisite for many validation activities but does not constitute validation.

VOIM Boundary with INTEGROS®

VOIM does not determine whether the Value Object possesses integrity.

INTEGROS® — Integrity Governance Architecture governs integrity.

An object can be sufficiently identified even while its integrity remains unknown or impaired.

VOIM Boundary with ADIT®

VOIM establishes the methodological identity of the Value Object for value governance.

ADIT® — Continuous Audit & Evidence Governance Architecture may govern evidence and auditability concerning that identification and subsequent events.

Identification ≠ Audit Evidence.

Minimum Implementation Framework

A minimum VOIM implementation should establish:

1. Value Object Candidate

Identify the subject proposed for value governance.

2. Object Reference

Establish the primary reference through which the subject can be distinguished.

3. Object Form

Determine whether the subject is physical, digital, informational, relational, capability-based, process-based, composite, or another governable form.

4. Distinguishability

Determine whether the subject can be sufficiently distinguished from adjacent objects or subjects.

5. Context Reference

Record contextual information necessary for identification.

6. Temporal Reference

Establish the relevant time or lifecycle reference where material.

7. Version / Configuration

Identify the relevant version or configuration where material.

8. Composite / Component Relationship

Record whether the Value Object forms part of, contains, or depends upon other Value Objects.

9. Identification State

Assign the governed Value Object Identification State.

10. Value Object Identifier

Create or associate a stable reference enabling the Value Object to remain traceable through the VFM® lifecycle.

Enterprise Application

VOIM gives organizations a foundational capability that is often missing from conventional valuation and economic systems:

the ability to establish exactly what is being treated as the subject of value before value is measured, priced, recognized, changed, taxed, impaired, restored, or transferred.

This becomes especially important where value does not map cleanly onto a conventional asset.

An organization may use VOIM to identify value objects such as:

unused production capacity; data; algorithms; intellectual property; infrastructure capability; technological potential; resource access; contractual opportunities; network relationships; dormant assets; recovered materials; digital capabilities; environmental resources; composite operational systems.

VOIM can therefore expose a fundamental error before it propagates through later analysis:

different parties may appear to disagree about value when they are actually assigning value to different Value Objects.

By making the Value Object explicit first, VFM® creates a stable reference for the entire downstream value lifecycle.

Foundational Principles

Value cannot be governed coherently until the subject of that value is identified.

Underlying Object ≠ Value Object ≠ Value.

Object existence does not establish value existence.

Value Object identification does not establish value recognition.

One underlying object may support multiple distinct value lifecycles.

One Value Object may consist of multiple underlying objects.

A Value Object may remain identifiable when its value reaches zero.

Potential value is not existing value.

Identification state is not value state.

Ownership is not required to identify a Value Object.

Price is not required to identify a Value Object.

A governable value lifecycle requires a sufficiently identifiable subject to which that lifecycle can remain anchored.

Canonical Closing Statement

Value Object Identification Module establishes the first methodological control point of VFM® — Value Flow Mechanisms Architecture by determining exactly what subject enters the governed value lifecycle as a Value Object. Through governance of Value Object Candidates, identification basis, object reference, distinguishability, object form, contextual reference, temporal reference, version and configuration awareness, composite and component relationships, identification states, and stable Value Object identifiers, VOIM prevents value governance from beginning with an ambiguous or undefined subject. By explicitly separating the underlying object from the Value Object and the Value Object from value itself, VOIM preserves the methodological boundaries between identification, value origin, value emergence, value recognition, value state, ownership, classification, validation, integrity, and audit. VFM® can therefore begin the lifecycle of value from a precise foundational question: before asking where value comes from, how it changes, whether it reaches zero, whether it can be restored, or when it becomes extinct, first establish exactly what the value is about.
