Canonical Definition

The Event Record Identification Module (ERIDM) governs how a
Determined Tax-Relevant Event receives a stable, distinguishable,
persistent, and traceable Event Record identity through which its
canonical governed representation can be referenced across
systems, organizations, transformations, and downstream
environments.

ERIDM establishes the authoritative association between the
Record being created and the Determined Tax-Relevant Event that
the Record represents.

Its principal transition is:

Determined Tax-Relevant Event

↓

Event Record Identification Governance

↓

Governed Event Record Identity

ERIDM does not identify the Event itself.

The Event has already been identified, formed, bounded, governed,
and determined through preceding TREGA™ layers.

ERIDM identifies its governed Record representation.

Its foundational distinction is:

Record Identity ≠ Event Identity.

Operational Role

After TREDS establishes a Determined Tax-Relevant Event, TREGS
requires a stable Record through which that Event can persist as
governed information.

Before Record structure, linkage, traceability, or
interoperability can be governed, the Record itself must be
identifiable.

ERIDM answers:

Which governed Record represents this Determined Tax-Relevant
Event?

The module prevents: anonymous Event Records; unstable Record
identifiers; accidental duplicate Record creation; confusion
between Event identity and Record identity; confusion between
canonical and technical representations; identifier reuse;
cross-system Record identity fragmentation; and loss of
Event-to-Record association.

Record Candidate

A Record Candidate is a proposed canonical representation of a
Determined Tax-Relevant Event entering TREGS Record Governance.

A Record Candidate shall reference a valid upstream TREDS
Determination.

A technical object does not become a governed Record merely
because it exists in a system.

Technical Object ≠ Governed Record Candidate by default.

Identification Eligibility

A Record Candidate becomes eligible for ERIDM governance where: a
valid Determined Tax-Relevant Event exists; the candidate is
intended to represent that Event; the Event-to-Record association
can be established; and no known identity conflict prevents
reliable identification.

Record Eligibility ≠ Record Identification Completion.

Record Identity Establishment

ERIDM establishes the governed identity of the Event Record.

The Record identity shall allow the Record to remain
distinguishable throughout its operational existence.

The identity should remain usable despite: storage migration;
schema transformation; API exchange; organizational transfer;
technical replication; or downstream consumption.

Record Identifier

A Governed Event Record Identity shall possess a stable
identifier or equivalent canonical reference mechanism.

The identifier shall distinguish the governed Record from other
Record identities within the relevant governance environment.

A Record identifier may be implemented through different
technical mechanisms.

ERIDM governs its methodological function rather than prescribing
a specific technology.

Identifier Uniqueness

A governed Record identifier shall be sufficiently unique within
its defined identification scope.

Two materially distinct Governed Event Records shall not
intentionally share the same canonical Record identifier.

Shared Identifier ≠ Shared Record Identity by default.

Identifier Scope

Uniqueness shall be evaluated within an explicit scope.

Possible scopes may include: system; organization; network;
platform; federation; or globally coordinated governance
infrastructure.

The scope shall be sufficient for the intended Record
interoperability.

Identifier Stability

A Record identifier should remain stable while the same governed
Record identity continues.

Technical changes should not create new canonical Record
identities unnecessarily.

Therefore:

System Migration ≠ New Record Identity.

Schema Change ≠ New Record Identity.

Storage Location Change ≠ New Record Identity.

Identifier Persistence

Record identity should persist for as long as the governed Record
must remain reconstructable.

Persistence is particularly important where the Record becomes:
inactive; superseded; corrected; archived; or replaced in
downstream systems.

A non-current Record may still require persistent identity for
historical reconstruction.

Identifier Immutability Boundary

Stable identity does not require every technical identifier to be
immutable.

Systems may replace internal keys or migrate technical
infrastructure.

ERIDM requires preservation of canonical identity continuity.

Technical Identifier Change ≠ Canonical Record Identity Change by
default.

Event-to-Record Association

Every Governed Event Record Identity shall be associated with the
Determined Tax-Relevant Event it represents.

The association establishes:

Governed Event Reference ↔ Governed Record
Identity

This association prevents the Record from becoming detached from
the Event Reality established upstream.

Association Cardinality

ERIDM shall not assume that every technical representation
creates a new canonical Record.

One governed Event may have: one canonical governed Record;
multiple technical representations; multiple system-specific
identifiers; multiple downstream copies.

These technical representations may reference the same canonical
Record identity.

Record Identity and Event Identity

Event identity and Record identity shall remain distinct.

The Event represents governed economic or operational reality.

The Record represents that Event as governed information.

Therefore:

Event Identifier ≠ Record Identifier.

A system may associate both, but shall not collapse their
methodological functions.

Record Identity and Technical Identity

A system may create: database primary keys; transaction IDs;
document IDs; message IDs; invoice numbers; ledger hashes; API
request IDs; internal object IDs.

These identifiers may contribute to Record identification.

They do not automatically become the canonical Governed Event
Record Identity.

Technical Identifier ≠ Governed Record Identifier by default.

Canonical Record Reference

ERIDM establishes a canonical reference through which other TREGS
modules and downstream systems can identify the same governed
Record.

The reference enables a common answer to:

Which governed Event Record are we discussing?

without requiring every system to use the same internal
identifier.

Identifier Mapping

Where multiple systems maintain different local identifiers,
mappings may associate them with the canonical Record identity.

ERIDM governs the identification meaning of that mapping.

Detailed cross-system interoperability belongs to ERINM.

Identifier Mapping ≠ Full Record Interoperability.

Record Identity Duplication

Duplicate identity occurs where multiple canonical Record
identities are unintentionally established for the same intended
governed Record.

ERIDM shall support detection and governance of potential
duplication.

Potential indicators include: same Event reference; same
Determination reference; overlapping Record creation; duplicate
ingestion; system retry; replicated processing; or migration
error.

Duplicate Record Candidate

Where multiple Record Candidates appear to represent the same
Determined Tax-Relevant Event, ERIDM shall not automatically
establish multiple canonical Record identities.

The candidates should be evaluated for whether they represent:
the same canonical Record; legitimate separate governed Records;
technical copies; or identity conflict.

Duplicate Candidate ≠ Duplicate Governed Record by default.

Identifier Collision

Identifier Collision occurs where the same identifier appears to
refer to materially different Record identities.

A collision shall be governed explicitly.

The system shall not resolve a collision merely by assuming the
records are identical.

Identifier Equality ≠ Record Identity Equality.

Identity Conflict

Record Identity Conflict exists where available identification
information supports incompatible Record identity conclusions.

Possible states include: Same Record; Different Records;
Duplicate Candidate; Collision; Ambiguous; Unresolved.

An unresolved material identity conflict should prevent
unqualified Record identification.

Record Identity Ambiguity

Ambiguity exists where the Record cannot yet be reliably
distinguished from one or more candidate Records.

Ambiguity may require: additional Event association;
Determination reference; technical-source reconciliation; or
escalation.

Ambiguous Record Identity ≠ Permission to Select an Arbitrary
Identifier.

Identifier Reuse

A canonical Record identifier should not be reassigned to an
unrelated governed Record after the original Record becomes
inactive, superseded, or closed.

Historical identity must remain reconstructable.

Inactive Identifier ≠ Available Identifier for Reuse by default.

Record Identity and Correction

A correction to Record content does not automatically create a

Whether identity remains continuous depends on whether the same

Record Correction ≠ New Record Identity by default.

Record Identity and Supersession

A superseding Record may require a distinct Record identity while

Record Identity and Event Correction

Where the underlying Event changes materially through upstream

That determination belongs to the authoritative Event-governance
layer.

ERIDM consumes the resulting Event identity state.

Record Identity and Merge

Where several Events are merged under TRERLS, existing Record
identities shall not automatically collapse into one identity.

A resulting governed Event may require an appropriate canonical
Record identity while prior Record identities remain traceable.

Event Merge ≠ Automatic Record Identifier Merge.

Record Identity and Split

Where one Event is split into multiple governed Events, the
original Record identity shall not automatically be copied to
every resulting Record.

Event Split ≠ Record Identity Replication.

Record Identity and Determination

If the same governed Record continues to represent the same

If Event identity or canonical representation materially changes,

Determination Reconsideration ≠ New Record Identity by default.

Cross-Organization Identity

Governance Requirements

ERIDM implementations shall ensure that: a valid Determined
Tax-Relevant Event exists before canonical Record identification;
the Record Candidate can be associated with the Event it
represents; Record identity remains distinct from Event identity;
canonical Record identity remains distinguishable from local
technical identifiers; identifiers are sufficiently unique within
their declared scope; identifier scope is explicit where
material; canonical identity can remain stable across technical
transformations; technical identifier change does not
automatically create new canonical identity; Record identity
remains persistent where historical reconstruction is required;
multiple technical representations do not automatically create
multiple canonical Records; duplicate Record Candidates can be
detected; identifier collisions are governed explicitly;
ambiguous identity does not result in arbitrary identification;
identifiers are not silently reused for unrelated Records; Record
corrections do not automatically create new identities; Event
Merge does not automatically merge Record identities; Event Split
does not automatically replicate Record identity; Determination
reconsideration does not automatically create new Record
identity; local system identifiers may map to canonical identity;
jurisdiction-specific tax identifiers remain downstream
references; machine-generated identifiers do not automatically
become governed Record identities; probabilistic confidence does
not replace governed identification; unresolved material identity
conflicts can be escalated; and the resulting Governed Event
Record Identity is suitable for ERSTM.

Governance Logic

IF no valid Determined Tax-Relevant Event exists, THEN ERIDM
shall not establish a canonical Governed Event Record Identity.

IF a Record Candidate cannot be reliably associated with a
Determined Tax-Relevant Event, THEN canonical identification
shall remain incomplete.

IF a technical identifier exists but no canonical Record identity
has been governed, THEN the technical identifier shall not
automatically become the Governed Event Record Identifier.

IF several technical representations refer to the same intended
governed Record, THEN ERIDM shall preserve one canonical identity
unless distinct governed Record identities are materially
justified.

IF two Record Candidates appear to represent the same Event and
same intended canonical Record, THEN duplicate resolution shall
occur before independent canonical identities are established.

IF the same identifier refers to materially different Record
identities, THEN Identifier Collision shall be established and
resolved before unqualified identification.

IF the same Record moves between systems while its canonical
governance identity remains unchanged, THEN canonical Record
identity shall persist.

IF a local technical identifier changes, THEN canonical Record
identity shall remain unchanged unless a materially new governed
Record has been established.

IF an Event Merge or Split changes the underlying governed Event
structure, THEN ERIDM shall consume the authoritative Event
result rather than infer new Record identity independently.

IF identity remains materially ambiguous or conflicted, THEN
escalation shall occur rather than arbitrary identifier
assignment.

IF Record identity and Event association are sufficiently
established, THEN ERIDM shall produce the Governed Event Record
Identity and hand it to ERSTM.

Enterprise Application

ERIDM provides the identity anchor for Event Record Governance.

A canonical enterprise pattern is:

Determined Tax-Relevant Event

→ ERIDM — Governed Event Record Identity

→ ERSTM — Governed Event Record Structure

→ ERLKM — Governed Event Record Linkage

→ ERTM — Governed Event Record Traceability

→ ERINM — Governed Event Record Interoperability

→ Governed Tax-Relevant Event Record

This enables different systems to reference the same governed
Record without forcing them to use identical technical
identifiers. Use Case 1 — One Marketplace Event Across Multiple
Systems

A marketplace Event has completed TREDS and exists as a
Determined Tax-Relevant Event.

The marketplace platform assigns transaction identifier A, the
ERP assigns object identifier B, the payment infrastructure uses
transaction reference C, and a downstream tax system creates
processing reference D.

ERIDM establishes one canonical Governed Event Record Identity
associated with the Determined Event and maps the relevant local
identifiers to that Record identity.

The four technical identifiers therefore remain distinguishable
technical references rather than four separate governed Event
Records.

An autonomous platform completes one governed service Event.

Because of distributed processing and retry logic, three

the same Determined Tax-Relevant Event.

Each candidate receives a different local system identifier.

Canonical Boundary

ERIDM owns the governance of Record candidate identification,
identification eligibility, canonical Record identity
establishment, identifier assignment, uniqueness, scope,
stability, persistence, Event-to-Record association, distinction
between canonical and technical identifiers, duplicate identity
detection, identifier collision, identity ambiguity, identity
continuity, identifier mapping at identification level, and
establishment of the Governed Event Record Identity.

ERIDM does not identify or determine the underlying Event.

It does not govern the full structural contents of the Record;
ERSTM owns Record Structure.

It does not govern broader Record Linkage; ERLKM owns that space.

It does not govern complete Record Traceability; ERTM owns that
space.

It does not govern cross-system semantic interoperability; ERINM
owns that space.

It does not govern Event lifecycle amendment, correction,
supersession, or closure; TRECLS owns those lifecycle functions.

It does not determine legal taxability, Tax Jurisdiction,
taxpayer status, Tax Base, Tax Rate, legal tax point, Tax Period,
Tax Liability, exemption, deduction, filing obligation, or other
jurisdiction-specific tax consequence.

Its governance begins when a valid Determined Tax-Relevant Event
requires a canonical Record identity.

Its governance ends when the Governed Event Record Identity and
its association with the underlying Event are sufficiently
established for Record Structure Governance.
